# 0008. Spry's core on Google Cloud

Status: accepted — 2026-11-16

## Context

By Lab 7 Spry runs on AWS and is described in Terraform. Lab 9 asks what it would take to run
the same system on Google Cloud, and what it would cost. The scope is the part that makes the
app usable: the frontend, the API and the database. Sign-in, the weekly report and the agenda
parser stay on AWS.

The constraints carried over from AWS:

- **No stored keys.** HCP Terraform reaches AWS through OIDC (ADR 0007). It must reach Google
  Cloud the same way.
- **$0 when idle, where the cloud allows it.** On AWS the API (Lambda) and the database (Aurora,
  min 0 ACU) both scale to zero.
- **The same code.** The backend image already runs outside Lambda (`docker compose up`).

The project is `spry-pelyno-2026` in `us-central1`. It belongs to the university's
organisation (`ucu.edu.ua`), whose policies allow everything below: public Cloud Run,
a public IP on Cloud SQL, and federation for `app.terraform.io`.

## Decision, row by row

| Spry on AWS | On Google Cloud | Decision |
|---|---|---|
| S3 + CloudFront + WAF, static frontend | **Firebase Hosting** | **Replace.** CDN and certificate included, free plan. `frontend/firebase.json` rewrites `/api/**` to Cloud Run: one origin, no CORS, as CloudFront's `/api` would. |
| Lambda + function URL, FastAPI | **Cloud Run** `spry-api` | **Replace.** The image's `runtime` target, the one Compose runs: uvicorn on `$PORT`. Min 0 instances, max 1. Mangum moved to a dependency group only the Lambda image installs. |
| ECR | **Artifact Registry** `spry` | **Replace.** Tagged with the commit SHA, keep the last 3 images (as the ECR lifecycle rule). |
| Aurora Serverless v2, 0–1 ACU | **Cloud SQL for PostgreSQL 17**, `db-f1-micro`, 10 GB SSD | **Replace.** See *The database* below. |
| DynamoDB | Firestore | **Not applicable.** Spry never left SQL. |
| Cognito + Google | Identity Platform | **Keep on AWS** (stretch). See *What stays on AWS*. |
| EventBridge Scheduler + SQS, weekly report | Cloud Scheduler + Pub/Sub | **Keep on AWS.** |
| S3 event → Lambda, the mailer | Cloud Storage + Eventarc → Cloud Run | **Keep on AWS.** |
| SES | no Google service | **Keep SES.** See *E-mail*. |
| Bedrock (Claude), agenda parser | Vertex AI | **Keep on AWS.** |
| Secrets Manager | **Secret Manager** `spry-database-url` | **Replace.** Generated by Terraform, read by Cloud Run as `DATABASE_URL`. |
| CloudWatch Logs | **Cloud Logging** | **Replace**, nothing to configure: Cloud Run's stdout lands there. |
| IAM roles | **Service accounts** | **Replace.** One per program: `terraform` (HCP Terraform acts as it) and `spry-api` (Cloud Run runs as it). The default compute account, which starts with Editor, is not used. |
| Terraform `aws` provider, workspace `spry-dev` | `google` provider, workspace **`spry-gcp`** | **A second root module** in `gcp/`, with its own state. One plan cannot break both clouds. |

### The database

| Option | Latency | Bill (idle month) | Code |
|---|---|---|---|
| **Cloud SQL, around the clock** | Same region as the API | ≈ $9.40 | None |
| Cloud SQL, stopped at night | Same, while running. Stopped, the API answers 503 | ≈ $1.70 + $0.0105 per running hour | None |
| Firestore | Same region | $0 within the daily free quota | Rewrite the data layer, models and migrations |
| Keep Aurora, call it across clouds | Every query crosses us-central1 ↔ us-east-1 (~30 ms). A page that runs 3 queries waits ~0.1 s more | $0.30, plus egress both ways | None, but Aurora has no public endpoint |

**Cloud SQL, with `make gcp-db-stop` / `gcp-db-start` for the nights.** The point of this lab is
to move the system, not to rewrite it. Spry has two related tables (`meetings` and `agendas`,
with a foreign key), Alembic migrations and a CI step (`alembic check`) that guards them.
Firestore would replace all of that with documents for $9 a month. Keeping Aurora would mean
giving it a public endpoint, or a VPN between the clouds, and paying egress on every query.

What Cloud SQL costs is the scale to zero. Aurora pauses, Cloud SQL does not. Stopping it is an
operation, not configuration: Terraform ignores `activation_policy`, so an apply does not start
it behind your back.

Connections go through the **Cloud SQL connector** that Cloud Run attaches (a Unix socket under
`/cloudsql`). The instance has a public IP and no authorised networks, so nothing can connect to
it directly. The connector checks IAM (`roles/cloudsql.client` on `spry-api`) and encrypts the
connection. No VPC, and no Serverless VPC Access connector billing by the hour.

**Data: migrations, then a copy through the APIs.** `pg_dump` from Aurora was not an option:
Aurora has no public endpoint, so a dump would need a bastion host in its VPC. The image runs
`alembic upgrade head` on start, which creates the schema on the empty database.
`make gcp-copy-data` then reads every meeting and agenda from the API on AWS and posts it to
the API on Google Cloud. The copies get new ids. **The two databases are copies, not
replicas.** AWS stays the source of truth, and the weekly report reports on AWS's data.

### E-mail

**Keep SES.** A multicloud architecture is allowed, and SES already sends the report from
AWS. If the report moved to Cloud Run, it would still call SES. It would not need an API key:
Cloud Run's service account gets a Google-signed ID token, and an AWS IAM role trusts
`accounts.google.com` for that account's unique id (`AssumeRoleWithWebIdentity`). That is
federation the other way round. With a third-party provider (SendGrid, Mailgun) the API key
would go into Secret Manager and reach Cloud Run as an env var, exactly as `DATABASE_URL` does.

### What stays on AWS, and why

- **Sign-in.** The user pool holds every account. Cognito never exports password hashes, so
  moving to Identity Platform means a password reset for everyone. The frontend on Google Cloud
  is built with sign-in off: Cognito's callback URLs list only the CloudFront site.
- **The agenda parser.** It is tuned for Claude (ADR 0006). Claude on Vertex AI is a partner
  model that the free trial's credit does not cover. Gemini would mean re-evaluating the prompt
  on a different model. The feature is off on the Google Cloud site, because the parser's
  function URL lets only the CloudFront origin through.
- **The weekly report.** It reads Aurora, the source of truth, and mails through SES. Moving it
  alone would report on the copy.

## How HCP Terraform reaches the project

`gcp/bootstrap/` is applied once from a laptop with `gcloud auth application-default login`.
It creates a workload identity pool `hcp-terraform` with an OIDC provider for
`https://app.terraform.io`. The provider's attribute condition admits a token only if
`terraform_organization_id` and `terraform_workspace_id` match: ids, not names, because a name
can be deleted and registered again by someone else. Only that workspace's principal set gets
`roles/iam.workloadIdentityUser` on the `terraform` service account. The workspace carries
`TFC_GCP_PROVIDER_AUTH`, `TFC_GCP_RUN_SERVICE_ACCOUNT_EMAIL` and
`TFC_GCP_WORKLOAD_PROVIDER_NAME`. Every run trades a fresh OIDC token for a short-lived token of
`terraform`. **No service account key exists.**

The `terraform` account has Cloud Run Admin, Cloud SQL Admin, Artifact Registry Administrator,
Secret Manager Admin and Service Usage Admin on the project, and Service Account User **on
`spry-api` only**, not project-wide. It cannot change the project's IAM policy. The one
project-wide grant the API needs (`roles/cloudsql.client`, since Cloud SQL has no per-instance
IAM) is made by the bootstrap instead. Secret access is granted on the one secret.

Same road as `spry-dev`: a PR gets a speculative plan, a merge to `main` applies (trigger
`/gcp/*.tf`). Terraform owns the service. `make gcp-deploy-backend` owns which image it runs
(`ignore_changes` on the image, as on Lambda).

## Consequences

- **The bill.** ≈ $9.40 a month idle against ≈ $0.30 on AWS, or ≈ $1.70 with the instance
  stopped. The free trial's credit pays for it during the lab. The full comparison is in
  `Lab9_submission.md`.
- **The API is public.** It is on AWS too: the function URL has `AuthType NONE`, and the
  meetings endpoints have no sign-in. Firebase Hosting's rewrite reaches Cloud Run as an
  anonymous caller, so `allUsers` has `run.invoker`. Sign-in with Identity Platform, verified by
  the API, is the stretch goal that closes this on both sides.
- **One instance.** `db-f1-micro` allows 25 connections. One instance's SQLAlchemy pool
  (5 + 10 overflow) fits, two would not under load. Max 1 instance also caps what a traffic
  spike can cost.
- **Lock-in.** The compute moved with no code change, the same image. The data moved with no
  code change either, because both clouds sell managed Postgres. The lock-in is in the managed
  services around them: Cognito, Bedrock, SES, EventBridge and the S3 events are why three
  features stayed behind.
- **Two databases.** Anything written on the Google Cloud site stays there. This is a migration
  rehearsal, not a multicloud deployment.
- **Clean-up** is `terraform destroy` in `spry-gcp` (APIs stay enabled, which costs nothing).
  The bootstrap goes after it, from the laptop.
